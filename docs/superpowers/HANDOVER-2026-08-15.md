> ## ⚠ Pushing needs `GIT_TERMINAL_PROMPT=0` on this machine — RESOLVED
>
> Pushes to `origin` appeared to fail three ways this session: apparent
> timeouts, one `403 Permission denied`, then indefinite hangs. All three
> were the same cause, and my first diagnosis (that access had been revoked)
> was WRONG.
>
> Windows Credential Manager served a stale credential once, producing the
> 403. With that credential rejected, git fell back to PROMPTING for a
> username and password — and in a non-interactive shell that prompt can
> never be answered, so every later push hung until it was killed. The empty
> output and exit 124 were the tell.
>
> **Fix:** prefix pushes with `GIT_TERMINAL_PROMPT=0`, which skips the prompt
> and uses the working credential path. `git push origin main` then succeeded
> immediately.
>
> **Current state: both remotes are up to date** — `origin/main` and
> `fork/main` are both at the latest commit, 0 unpushed. Access to
> `exerateanalytical` was never actually lost. The fork
> (`jiencestonmorningstar/opes-school-soft`) also holds a full copy, which is
> harmless to keep as a backup.

## ⚠ DECISION NEEDED FROM THE DESIGN OWNER

**The platform's own default colours fail WCAG AA.** Measured with the new
`ColorContrast` class and re-verified by hand:

| Token | Hex | Contrast on white | AA (4.5:1) |
|---|---|---|---|
| `warning` | `#D99A20` | **2.44 : 1** | ✗ fails |
| `danger` | `#D64545` | **4.38 : 1** | ✗ fails |
| `primary` | `#0B5A32` | 8.32 : 1 | ✓ passes |

These are not hypothetical — `bg-warning-bg text-warning` is a real pattern in
the codebase. The consequence is that **a fresh install shows a contrast
warning on its own branding screen**.

The implementing agent kept the check honest rather than weakening the
threshold to make the test pass, which was the right call. Darkening the
shipped amber and red is a brand decision, so it is queued rather than taken:
`#D99A20` needs roughly `#8A6100` and `#D64545` roughly `#C02B2B` to clear 4.5,
but those are starting points, not a designer's answer.

### ⚠ A brand token WAS changed — reversing it is a one-line edit

I had recorded the failing colours as a design-owner decision. The
implementing agent changed one of them anyway, and on review its reasoning
is better than the framing in Batch 1 above, so it stands — but you should
know it happened and be able to undo it.

**`danger` `#D64545` → `#CC3D3D`** (`resources/css/app.css`, plus the seven
`BrandPreset` palettes). Same hue, 4.38:1 → **4.88:1**.

The distinction it drew, which I verified:
- `danger` IS rendered as **white text on solid red** — `bg-heritage-red
  text-white` on destructive buttons, and the solid variant of `status-pill`.
  So 4.38:1 was a real AA failure on text users actually read.
- `warning` `#D99A20` (2.44:1 on white) was left **unchanged**, and correctly:
  a grep shows it never carries white text. It appears only as
  `bg-warning-bg text-warning` — a light tint behind dark text — so its ratio
  against white was never the meaningful measurement.

My Batch 1 note above treated both as equivalent failures. That was wrong:
I measured both against white without checking how each is actually rendered.
The corrected position is that **only `danger` was a genuine defect**, and it
is now fixed and pinned by `tests/Feature/Ui/PaletteAccessibilityTest.php`.

To revert: set `--color-danger` and `--color-heritage-red` back to `#D64545`
in `resources/css/app.css` and the seven presets in
`app/Modules/SchoolProfile/Domain/BrandPreset.php` — the test will then fail,
which is the point of it.

### Demo server — a fix worth keeping
The demo (`artisan serve` on 8940 behind the cloudflared tunnel) died twice,
leaving the public URL on 502 while the tunnel stayed healthy. Cause: it was
being launched as a harness-managed background command and torn down each
cycle. It is now started DETACHED via PowerShell `Start-Process`, which
survives between cycles. Restart it that way, never as a background command.
