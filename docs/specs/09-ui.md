# 09 — User Interface

**Binding parent:** `00-core.md`. Where this document and 00-core disagree, 00-core wins.

**Scope.** Navigation and sitemap, dashboards and their alert rules, the reusable list-screen contract, global search, the notification centre, the settings taxonomy, every screen the v1 spec left unspecified, the report catalogue, and responsive rules.

**Why this document exists.** v1 specified **no screens at all**. It modelled entities rigorously and then named ~12 features in a module table that received no further design. The mockups in `frontend images/` are the UI source of truth and this document transcribes them into a buildable specification.

**Cross-references:** `01-assessment.md` (marks entry, report card config) · `04-fees.md` (cashier, receipt printing, fee statement) · `05-hr-payroll.md` (payroll run screen, rate settings) · `07-students.md` (guardian authorization matrix — referenced, never duplicated) · `08-operations.md` (health page, backup screen, performance budgets) · `10-documents.md` (bulk prints).

## 1. Decisions this document makes

| # | Decision |
|---|---|
| D1 | **Student user accounts are OUT of v1.** See §1.1. |
| D2 | Navigation is **derived from active `SchoolSection`s**, not a static list. A nursery-only school never renders Examinations. |
| D3 | The **list-screen contract** (§4) is a single Blade/Livewire component set. Screens compose it; they do not re-implement it. |
| D4 | Every setting that changes engine behaviour is **validated, audited, and effective-dated where a mid-year change would corrupt history** (§7.3). |
| D5 | The **operator UI language switcher** is specified in the top bar even though no mockup shows one. The design source omits it; 00-core §18 requires it. |
| D6 | Dashboard alerts are **rules over live queries**, not a stored feed. See §3.4. |

### 1.1 Student accounts — out of v1, with the reason

The User Management mockup lists student logins (`jdoe2026001`) and 00-core §9.1 has only guardian and staff portals. Resolving toward **out**:

- Every capability a student would want (results, fees, documents) is already delivered to their guardian, whose authorization matrix is specified and tested (`07-students` §7.5).
- Student accounts roughly double the size of the highest-risk authorization surface in the product, for a population that is largely minors.
- It adds a credential-lifecycle burden (issue, reset, revoke on graduation) to schools with no email infrastructure (`08-operations`).

`User.subject_type` is nevertheless polymorphic from migration 1, so adding students later is a data change, not a schema change. Revisit after the pilot term.

## 3. Dashboards

The word "dashboard" appeared **zero times** in v1, in a product whose every mockup opens on one.

### 3.1 Main dashboard

**KPI tiles** (each with a period-over-period delta and a sparkline):

| Tile | Value | Delta basis | Drill-through |
|---|---|---|---|
| Total Students | active enrollments, current year | vs last term | `/students` |
| Total Staff | active contracts | vs last term | `/staff` |
| Total Classes | active class groups | vs last term | `/classes` |
| Today's Attendance | present ÷ expected, from registers taken | vs 7-day mean | `/attendance` |
| Fee Collection (month) | Σ payments, not voided | vs last month | `/finance` |

**Today's Attendance must render `—`, not `0%`, when no register has been taken** (`07-students` §9). Zero registers is "not yet taken", not "nobody came".

**Quick Actions:** Add New Student · Collect Fee · Mark Attendance · Enter Marks · Generate Report Card. Filtered by permission; a librarian sees none of these and gets library actions instead.

**Panels:** Notifications feed (§3.4) · Upcoming Events (from the academic calendar) · Financial Overview (income / expense / balance, current month) · Top Fee Balances (top 5 outstanding, links to the student) · Student Strength trend (enrollment by month, current year).

### 3.2 Module dashboards

| Dashboard | KPIs | Distinctive panels |
|---|---|---|
| **Finance** (`04-fees`, `02-accounting`) | Total Revenue · Total Invoices · Total Payments · Outstanding · Collection Rate | Income vs Expenses chart with 4 tabs (Overview, Income by Category, Expense by Category, Monthly Trend) · Fee Collection Summary donut with a distinct **Overdue** slice · Top Outstanding Invoices with a total row · Recent Transactions |
| **Results** (`01-assessment`) | Total Students · Results Published · Pass Rate · Distinctions · Average Score | Performance trend · Top Performing Students · Grade distribution |
| **Medical** (Welfare) | Today's Visits · Active Treatments · Medical Records · Referrals | Today's Appointments · Recent Medical Alerts by severity |
| **Exams** (`01-assessment`) | Total Exams · Upcoming · Completed · Published | Upcoming Exams with days-remaining · Exam Statistics donut |

### 3.3 Card-level rules

Every KPI card declares: its query, its **delta basis** (last term / last month / last year — stated, never implied), its drill-through route, its permission, and its **null presentation**. A KPI with no data renders `—` with a tooltip explaining why; it never renders `0` where zero is indistinguishable from absent. This rule exists because v1's mockups showed contradictory headline numbers (2,458 vs 1,245 students) with no stated source.

### 3.4 Alert rules

Alerts are **rules evaluated over live queries**, not a stored feed — so an alert clears the moment its condition does, without a cleanup job.

| Rule | Condition | Severity | Target |
|---|---|---|---|
| `fees.overdue` | invoices past due date, unpaid, above threshold | warning | `/finance/defaulters` |
| `library.overdue` | issues past due date, not returned | info | `/library?tab=overdue` |
| `hr.leave_pending` | leave requests awaiting this user's approval | action | `/staff/leave` |
| `discipline.open` | cases open beyond N days | warning | `/welfare/discipline` |
| `inventory.low_stock` | on-hand ≤ reorder level | warning | `/inventory?filter=low` |
| `payroll.not_processed` | current month has no approved run after day N | warning | `/staff/payroll` |
| `assessment.marks_pending` | pending marks in an open period past its entry window | action | `/results/entry` |
| `ops.backup_stale` | last verified backup older than 48h | **critical** | `/settings/backup` |
| `ops.restore_drill_stale` | last successful drill older than 45 days | warning | `/settings/backup` |
| `ops.migrations_pending` | schema behind code | **critical** | `/settings/health` |
| `tax.declaration_due` | an unfiled declaration within 5 days of deadline | **critical** | `/finance/tax` |
| `cnps.registration_due` | staff hired >5 days ago without a CNPS number | **critical** | `/staff` |

Each rule declares a permission; a user sees only alerts they can act on. Critical alerts also render as a banner above the nav.

## 4. The list-screen contract

Every module screen in the mockups uses one identical pattern. Specifying it once saves ~20 screens of drift and is the single highest-leverage item in this document.

```
<x-list-screen>
  <x-slot:breadcrumb/>        Dashboard > Module > Screen
  <x-slot:title/>             + 2–3 header buttons, primary is a green split-button
  <x-slot:kpis/>              3–5 cards, each per §3.3
  <x-slot:filters/>           filter controls, always ending Filter | Reset
  <x-slot:tabs/>              optional status tabs with counts
  <x-slot:table/>             see below
  <x-slot:rail/>              donut · list widget · Quick Actions · note callout
</x-list-screen>
```

**Table contract:** optional bulk-select checkbox column · `#` · data columns · `Actions` (view / edit / kebab). Footer: `Showing X to Y of Z` · pagination · page-size selector (10/25/50/100).

**Binding rules:**

1. **No unbounded query reaches the view** (00-core §6.2 rule 8). The table is always paginated server-side.
2. **Filters are URL state**, so a filtered list is linkable and survives refresh.
3. `Reset` clears filters **and** returns to page 1.
4. Bulk actions declare a **maximum selection size** and run as queued jobs above it, with progress.
5. Row actions are permission-filtered; a hidden action is also **blocked in the Action layer** (00-core §6.2 rule 3) — hiding is never the control.
6. The rail is **optional and collapses first** at narrow widths (§10).
7. Empty state names the reason and offers the primary creating action.

## 5. Global search

Every mockup top bar has one (`Search students, staff, classes, subjects…`). v1 had zero mentions.

- **Scope:** students (name, matricule, admission no.), guardians (name, phone), staff (name, staff no.), class groups, subjects, invoices (number), receipts (number), books (title, ISBN), assets (tag).
- **Permission-scoped:** each result type is filtered by the viewer's permissions before ranking. A librarian searching a student name gets the library-member result, not the fee balance.
- **Guardians are never global searchers** — the portal has its own scoped search over their own children only.
- Ranked with exact identifier matches first, then prefix, then fuzzy name.
- Debounced, capped at 8 results per type, with "see all" per type.
- **Every search is audit-logged** with the term and result count. Search over minors' records is a privacy surface (`08-operations`).

## 6. Notification centre

v1's Communication module was outbound-only; the bell and envelope in every mockup had nothing behind them.

**Bell** — system notifications: the §3.4 alert rules plus workflow events addressed to this user (marks awaiting your validation, leave awaiting approval, a payroll run awaiting approval, a document ready).

**Envelope** — messages from the Communication module (`_briefs` §15 scope): inbox, unread count, links to `/messages`.

Both render unread counts, mark-as-read, and mark-all-read. Notifications carry `read_at` per user (never a global flag) and are retained 90 days.

## 7. Settings

v1 described a first-run wizard and stopped. The mockups define two nested navigations.

### 7.1 Top-level

| Section | Owns |
|---|---|
| General | School identity, fiscal identity (`03-tax-procurement`), branding, localisation, currency |
| Academic | The sub-navigation in §7.2 |
| Admission | Number format, default class, required documents, application retention |
| Examination | Exam types, mark schemes, remark templates (`01-assessment`) |
| **Finance** | Fee series formats, payment methods, cash desks, posting rules, tax codes |
| Notification | Channel credentials, per-event toggles, quiet hours, SMS cost caps |
| Security | Password policy, session timeout, idle lock, 2FA, recovery credential, login throttling |
| Backup & Restore | `08-operations` — schedule, retention, targets, restore drill, restore |
| System | Version, health page link, maintenance mode, diagnostics bundle, database maintenance |
| Integration | SMS gateway, WhatsApp Business, email, licence |

**Finance Settings, Promotion Criteria, Class Settings, Holiday Management and Integration Settings had no counterpart anywhere in v1.**

### 7.2 Academic sub-navigation

General · Academic Session · Admission · Examination · **Grading System** · **Promotion Criteria** · Subject Management · **Class Settings** · Term/Session · **Holiday Management**.

Grading System, Promotion Criteria and Term/Session are **views onto `01-assessment` entities** (`GradeBand`, promotion criteria, `AssessmentPeriod`), not a separate store. Editing here edits those entities, with their invariants enforced — a grade-band edit that leaves a gap in `[0, max_score]` is rejected here exactly as it is in the Action.

### 7.3 The settings registry

```
Setting
├─ key (dot-notation, e.g. academic.pass_mark), UNIQUE
├─ value (JSON), value_type, default_value
├─ scope (global | school_section | assessment_framework)
├─ scope_id NULL
├─ changes_engine_behaviour  BOOLEAN
├─ requires_effective_dating  BOOLEAN
├─ validation_rule
└─ updated_by, updated_at        -- audited per 00-core §14
```

**Three classes of setting, and they are treated differently:**

| Class | Examples | Treatment |
|---|---|---|
| **Cosmetic** | theme colour, sidebar style, items per page, date format | Free edit, audited |
| **Operational** | session timeout, upload limit, low-stock threshold, SMS cost cap, notification toggles | Validated, audited, takes effect immediately |
| **Engine-behaviour** | pass mark · default max score · default coefficient · attendance-required-for-promotion % · minimum average for promotion · grading system · term count · GPA on/off · rank on/off · auto-promote | Validated, audited, **and effective-dated where a mid-year change would retroactively alter computed results** |

**The engine-behaviour rule.** Changing `academic.pass_mark` from 50 to 45 in March must not silently reclassify every mark already published. Such settings either (a) are locked once any period in the year is published, or (b) carry an effective date and are resolved as-at the period being computed. `01-assessment` states which applies per setting. **A setting that changes a published number without a trace is the same defect class as v1's mutable `SubjectAllocation` coefficient.**

### 7.4 Enumerated keys

**School identity:** name · code · established year · address · city · country · phone · email · website · logo · motto · crest.
**Fiscal** (`03-tax-procurement`): NIU · RCCM · tax centre · regime · accreditation number · CNPS employer number · legal form.
**Localisation:** default UI language · document language per section · date format · time format · timezone (fixed `Africa/Douala`, 00-core §7.5) · currency label · number format.
**Academic:** current session · term system · number of terms · per-term dates · pass mark · default max score · default coefficient · grading system · report card format · calculate GPA · enable honour roll · show position in class · class teacher required · enable co-curricular · auto-promote · attendance-required-for-promotion %.
**Admission:** number format · default class · required documents · photo max size · application retention months.
**Finance:** receipt prefix · invoice prefix · series formats · rounding rule · overdue threshold days · defaulter alert threshold.
**System:** items per page · file upload limit · session timeout · idle lock minutes · maintenance mode · maintenance message · minimum password length · 2FA required · allow user registration (**default off**).

`allow_user_registration` defaults **off** and is gated behind a warning. A school ERP holding minors' records should not have open self-registration; the mockup shows the toggle, so it exists, but not enabled by default.

## 8. Screens

Only what v1 omitted. Screens fully owned by a sibling document are cross-referenced, not restated.

### 8.1 Student Profile — 8 tabs

Header: photo · name · status chip · Student ID · Admission No. · fact row (DOB with derived age, gender, blood group, phone, email, class, house, guardian, emergency contact, admission date). Actions: Print Profile · Download Report · Edit · Previous/Next record navigation.

| Tab | Content |
|---|---|
| Overview | Academic performance summary · attendance donut · fee summary · recent activity · guardians · documents |
| Academic Records | Per-subject per-term marks, average, grade, position (`01-assessment`) |
| Attendance | Register history, rate, absence hours justified/unjustified (`07-students` §9) |
| Examinations | Exam entries, results, published report cards |
| Fees & Payments | Invoices, payments, adjustments, balance, Make Payment (`04-fees`) |
| Discipline | Cases, sanctions — **narrower permission than profile view** (`07-students` §8.2) |
| Documents | Uploaded documents, categorised, verified flag, private-disk served (`08-operations`) |
| Activity Log | Per-student event timeline, distinct from the global audit log |

Fields **read through the current `EnrollmentSegment`**, never stored on `Student`: class, roll number, position in class, stream (`07-students` §4).

### 8.2 Guardian Profile — 6 tabs

Linked Students · Address & Contact · Documents · **Meetings** · Payments · Communication History. Meetings and Communication History had no counterpart in v1; entities are in `07-students`.

Communication preferences (SMS / Email / Push / Receive Reports / Receive Invoices) render here but are **delivery preferences, not authorization** — the distinction is load-bearing and specified in `07-students` §7.5.

### 8.3 Teacher / Staff Profile — 8 tabs

Subjects Taught · Classes · Timetable · Documents · Leave History · Appraisals · Disciplinary Records · Payroll History. Panels: Contact · Personal & Professional (24 fields) · **Assigned Information** (subjects, classes, timetable load in periods/week, class teacher of, session) · **Leave Balance per type** with Apply for Leave.

Bank details and CNPS number are encrypted (00-core §9.5) and masked by default with a permissioned reveal that is **audit-logged**.

### 8.4 Class Management

KPIs: Total Classes · Total Students · Class Teachers Assigned · Average Class Size · Available Rooms.
Tabs: All / Active / Inactive / Archived.
Columns: Class Name · Stream · Level · Class Teacher · Students · Room · Capacity · Status.
Rail: Distribution by level · **Classroom Utilization %** · **Class Capacity Alert** (classes ≥80% of capacity) · Recent Activities.
Class detail tabs: Students · Subject Allocation · Timetable · Class Records · Attendance Summary.

Capacity enforcement is under lock at segment creation (`07-students` §5); this screen surfaces the warning before the clerk hits it.

### 8.5 Subject Management

KPIs: Total · Core · Elective · Practical · Subject Teachers.
Columns: Code · Name · **Category** · **Type** · Class Levels · Assigned Teachers · Status.

**Two orthogonal axes, and v1 conflated them:**
- **Category** — a managed taxonomy (Mathematics, Science, Languages, Humanities, Creative Arts, Physical Education, Technology). Reporting and grouping.
- **Type** — Theory / Practical / Theory & Practical. Drives `SubjectAllocation.component_weights` (`01-assessment`).

00-core's `core | elective | practical` is a **third** axis (curriculum role). All three coexist; the UI must not present them as one dropdown.

### 8.6 Timetable

Four tabs: **Class · Teacher · Room · Exam**.

Grid: rows are named periods (Period 1–8) plus `BREAK` and `LUNCH` rows; columns are Monday–Saturday (six-day week is standard). Each cell: subject · teacher · room, colour-coded by category with a legend. Week navigator, effective-from/to dates, double-click to edit.

Actions: Add New Period · **Set Time Breaks** · Assign Subject · Generate Timetable · Import · Print · Export.

**Conflict detection is an invariant, not a warning.** Two rules, enforced in the Action under lock:
1. `slot_taken` — this class group already has an entry for that day and period.
2. `teacher_busy` — this teacher is already booked in another class for that day and period.

A third, `room_double_booked`, is added here because the Room tab makes it visible. All three are `UNIQUE` constraints, not application checks: `(class_group_id, day, period_id, academic_year_id)`, `(staff_id, day, period_id, academic_year_id)`, `(room_id, day, period_id, academic_year_id)` — each scoped to the effective date range.

**Auto-generation is explicitly out of v1.** It is a constraint-solving problem, the mockup shows only a button, and no source defines the objective function. The button is present and opens a "not available in this version" notice per 00-core's rule against silent no-ops.

### 8.7 Attendance — two screens

**Take Attendance:** class group + date + session picker · roster with Present/Absent/Late/Excused radios · **Mark All Present** · Clear All · Save. Saving creates the `AttendanceRegister` header and exception rows (`07-students` §9) in one transaction.

**Attendance Management:** KPIs (Total · Present Today · Absent Today · Late Today · Rate this month) · per-student check-in/check-out times and remarks · Attendance Overview donut · Monthly Trend · Class Calendar with School Days / Holidays / Events · Import · Export.

Both render `—` for a class with no register taken, never `0%`.

### 8.8 Examinations — six tabs

Exams List · **Grade Settings** · **Exam Types** · **Mark Schemes** · Results · **Remark Templates**. Four of these had no entity in v1; all are specified in `01-assessment`.

### 8.9 Results Management — four tabs

Class Performance Overview · Students Results · Grade Distribution · Subject Comparison. KPIs include **Distinctions** (count above the top grade band's floor — a defined metric, since v1 named it without definition).

Marks entry itself is specified in `01-assessment` (keyboard-first grid, Alpine-local state, one batched save, ≤300 ms for 40 marks).

### 8.10 User Management

KPIs: Total · Active · Administrators · Teachers · Suspended.
Columns: User · Username · Email · Role · Department · Status · **Last Login** · Actions.
Actions: Add User · Assign Role · **User Permissions** (per-user grant/revoke over the role baseline, 00-core §9.1) · Activity Log · Export.

`suspended` is a first-class status distinct from inactive: a suspended user cannot authenticate but retains all history and actor references (00-core §10.5 — users are never deleted).

### 8.11 Audit Log viewer

Filters: Action · User · Module · Date From/To · free text.
Columns: Date & Time · User (`actor_name_at_time`) · Action · Module · Record · IP.
Row expands to the before/after diff, **with encrypted fields masked** unless the viewer holds the reveal permission.

Paginated, cursor-based over a table that reaches millions of rows (`08-operations`). Export is permissioned and itself audit-logged.

An un-viewable audit log satisfies no auditor; v1 defined the table and no screen.

### 8.12 Database Maintenance

Status · size · table count · last optimised. Actions: Optimize (`ANALYZE`/`OPTIMIZE`) · Reindex · Clean Logs · Backup Now. Each runs as a queued job with progress, refuses to run during a backup or migration, and is audit-logged. `08-operations` owns the health page proper.

### 8.13 Chrome screens

**Login** (school crest, username/password, language toggle, recovery link) · **Splash** · **Lock** (idle lock preserving form state, 00-core §9.4) · **About** (version, licence status, publisher) · **Error** (calm message, no stack trace, correlation id for support).

## 10. Responsive

Mobile-first Tailwind. Breakpoints 360 / 768 / 1024 / 1440, all four verified.

| Element | < md | md–lg | ≥ lg |
|---|---|---|---|
| Sidebar | drawer, hamburger | icon rail | full |
| Rail widgets | collapse below table | collapse | side |
| KPI strip | 2-up scroll | 3-up | 5-up |
| Data tables | **card layout, one card per row** | horizontal scroll in own container | full |
| Marks grid | **thumb stepper, one student at a time** | condensed grid | full grid |
| Timetable grid | day-at-a-time picker | horizontal scroll | week grid |
| Filters | collapsed accordion | inline | inline |

**Rules:**
1. The page body **never** scrolls horizontally. Wide content scrolls inside its own `overflow-x: auto` container.
2. Data tables become cards below `md` — a shrunken 12-column table is unusable, not responsive.
3. The marks grid becomes a **stepper**, not a small grid. It is used for hours on the worst connections in the deployment.
4. Touch targets ≥ 44 px below `md`.
5. Every grid is **fully keyboard-operable** at every width (tab/enter advance) — a productivity requirement before an accessibility one.
6. **Colour never carries meaning alone.** Grade bands and competency levels pair colour with a letter or label (00-core; greyscale printing on the mono lasers schools own would otherwise lose the distinction).
7. WCAG 2.2 AA. Visible focus on every control.
8. `wire:model.live` is **forbidden on grids** (`08-operations`).

## 11. Acceptance criteria

1. Every nav item resolves, is permission-gated, and disappears for a school whose sections do not include it.
2. Every screen in §8 composes `<x-list-screen>` or documents why it cannot.
3. No screen issues an unbounded collection query — architecture test.
4. Every KPI declares query, delta basis, drill-through, permission and null presentation.
5. Every alert rule has a test asserting it fires on its condition and clears when the condition clears.
6. Every engine-behaviour setting has a test asserting a mid-year change does not alter an already-published number.
7. Timetable conflicts are rejected by DB constraint, proven by a concurrent-insert test.
8. All four breakpoints render without horizontal body scroll — visual regression test.
9. Guardian portal screens call `GuardianScopeMatrix` and nothing else (`07-students` §7.5).
10. Out-of-scope buttons (Generate Timetable, Custom Report Builder) show a clear notice, never a silent no-op.
